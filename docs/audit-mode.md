# Audit mode — certifying a migration this pipeline did not perform

The four-layer verifier never cared who wrote the Java. It runs both
sides, diffs their behaviour, and reasons about the IR. Only `certify`
cared, because it read the winning artifact out of `migrate`'s
`selection.json` — so a module could not be certified unless this
pipeline had generated it.

That coupling was accidental, and removing it changes what the product
can be sold as.

## Why this matters commercially

Coverage is the hard constraint on selling migration: of 31 real AWS
CardDemo modules, 3 are eligible and 17 do not parse (they `COPY` CICS
copybooks that ship with CICS). If the pitch is "we migrate your COBOL",
that number ends the conversation.

Audit mode inverts it. Enterprises are **already** migrating COBOL — with
systems integrators, with vendor tools, in-house — and none of them can
prove the result is equivalent. In that engagement:

- **refusal is a feature.** "We cannot verify this module, here is
  exactly why" is what an auditor is *for*. In a migration contract the
  same sentence is a failure.
- **coverage stops being a gate.** Certifying 3 modules of 31 is a
  catastrophe if you promised a migration and a reasonable start if you
  price per certified module.
- **it is counter-positioned.** The party doing the migration cannot
  credibly audit it.

This was demonstrated accidentally: `CBACT02C` passed layers A and B
against the real GnuCOBOL binary using **hand-written** Java. The
verifier neither knew nor cared.

## Using it

```bash
legacymind certify --audit-java <Main.java> --layer-b <layer-b.json> --ir <module.ir.json> --out certification.json
```

with `--layer-a` / `--layer-c` / `--layer-d` as available, exactly as in
migrate mode. The verdict rule is unchanged: layer B must pass, at least
one other layer must have run, and every layer that ran must pass.

`--ir` is **required** here. In migrate mode `selection.json` identifies
the module; in audit mode nothing else does, and a certificate that
cannot say what it certified is not worth issuing.

## What the certificate says differently

The signed body records provenance explicitly rather than leaving fields
empty for a reader to interpret:

```json
"target": {
  "file": "…/Cbact02c.java",
  "sha256": "47bd4d89…",
  "provenance": "supplied — this artifact was NOT generated by this pipeline",
  "model": null,
  "candidate": null
},
"selection": {
  "mode": "audit",
  "note": "no candidate selection: the Java artifact was SUPPLIED, not generated by this pipeline. This certificate is evidence about that artifact, and about nothing upstream of it."
}
```

and the rendered report leads with it:

> **Audit certificate.** The Java artifact was supplied, not produced by
> this pipeline. This is evidence about that artifact and about nothing
> upstream of it — it says nothing about how the code was written, or by
> whom.

The transpiler-model and cost rows are **omitted** rather than printed as
`null`, because a `null` invites a reader to assume an omission where the
truth is "there was no model".

Every layer report is still checked to have tested the same artifact: in
migrate mode the token is `candidate-<id>`, in audit mode it is the
supplied class name, and a layer whose modern side does not reference it
raises a gap.

## First use — the first certificate over real third-party code

`CBACT02C`, untouched AWS CardDemo, audited against the real GnuCOBOL
3.1.2 binary reading a real VSAM file:

| layer | status |
|---|---|
| A — property, 200 generated record sets | PASS |
| B — curated, byte-for-byte (`raw`) | PASS |
| C — symbolic | NOT_RUN — status-driven read loop (`docs/read-loop.md`) |
| D — static data-flow | NOT_RUN — examined nothing (`docs/raw-protocol.md`) |

**Verdict: CERTIFIED**, signature verified, with two gaps on the face of
it: layer C not run, and the `CEE3ABD` external-service disclosure.

That is a **weaker envelope than the benchmark's four-layer modules**, and
the certificate says so. It is also the first signed statement this
project has made about code it did not write.

## What audit mode does not change

- **The demo key is still a demo key.** Re-sign with a production key
  before any certificate leaves the building.
- **Coverage is still coverage.** Audit mode certifies what the subset
  reaches; `assess` still tells the customer what it does not.
- **A hand-written artifact is fine to audit and useless as evidence
  about the transpiler.** That is the entire point of the provenance
  field, and it is why the migration path still requires a real `migrate`
  run (`docs/first-real-certificate.md`).
